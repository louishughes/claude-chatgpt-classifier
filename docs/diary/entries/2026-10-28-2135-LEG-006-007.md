### 21:35 — LEG-006 and LEG-007: one big message no longer stops a run, and waiting requests find their run

**What:** Two failures from the PC's size-only run. First, `ke classify run` and `ke digest run` stopped all 50 chats when a single request was bigger than one request file (100,000 characters); one real message is about 114k characters on its own. Now that request is recorded as "too big", never sent, and the rest of the run goes ahead, the way `ke extract run` already behaved. Second, a request waiting from an earlier run could not be collected once a new run ID was used, because the ledger kept its batch numbers but not its run. Each request now remembers its run and is collected from that run's folder, and a request whose batch files were deleted is simply asked again in the current run.

**Why this way:** Long segments are already split at exchange boundaries (LEG-005); what's left over is one message that can't be split without cutting someone's words in half, so a person should see it. The PC thread had to delete 163 orphaned rows by hand; with the run stored, that can't happen again, and a deleted folder now costs one re-ask, not a stuck stage. A request file that was *changed* is still refused.

**Teach-back (`ModelStageRunner` in `providers/ledger.py`):** Before anything is sent, the runner checks each request against the provider's own size limit and records the ones that don't fit instead of crashing. When it collects, it groups waiting requests by the run they were written to and reads each group from that run's folder. If a request isn't in any batch file still on disk, it's treated as a provider hiccup and written again into the current run.
