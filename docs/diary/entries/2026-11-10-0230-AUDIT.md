### 2026-11-10 02:30 UTC — Codebase audit: what to delete, simplify or question

**What:** Louis asked for a hard look at the whole codebase: what is unnecessary, over-complicated or resting on weak assumptions, then to make the changes, preferring delete over simplify over optimise over automate. The full findings are in `docs/reviews/CODEBASE_AUDIT_2026-11-10.md`.

**How "unnecessary" was decided:** not by taste. A script mapped which modules import which, another counted every function's callers in production code and in tests separately, and vulture (a dead-code finder) checked the rest. Each finding was then checked against `STATUS.md`, the ADRs and `OPEN_DECISIONS.md` to see whether the piece was actually wanted.

**What changed (no test touched):**
- Deleted `_not_built` from `cli/main.py`: a placeholder for unbuilt commands that nothing calls any more, because every command is built.
- 28 modules each had their own private copy of the same two-line "what time is it in UTC" function, and three had the same "put the UTC time zone back" helper. Both now live once, as `utc_now()` and `as_utc()`, in `infrastructure/db.py`. About 125 lines fewer, same behaviour.

**What I found but did not change (needs Louis):** the big wins are whole features, and removing them would also remove their tests, which only Louis can approve.
- About 2,700 lines of hosted, multi-user code (JSON API, accounts and tenants, a PostgreSQL trial) that the project's own decision record (OD-19) calls "built and tested but unused", and that the scope decision had labelled *parked*.
- Three more parked integrations (website fetching, YouTube captions over OAuth, watched folders) that were built anyway.
- Code only the tests call, two note templates running side by side, a throwaway spike folder, instruction files that still say "no application code yet", and the same ticket write-up kept in four places.

**Challenges:**
- **The premise didn't match the record.** The request said thousands of customers use the product; the repo's decisions say it is a one-person local tool and that nobody else's data should go in before an independent security and data-protection review. I worked to the strict standard either way and put the question first in the report, because the answer decides whether the hosted code should be deleted or is essential.
- **Dead-code tools over-report.** vulture flags web routes, database columns and validators as "unused" because frameworks call them, not our code. Every hit was checked by hand; most were false.
- **A borderline case kept.** `relationship_key.key_schema` has no callers, but it belongs to the answer-key tooling that an independent session on the PC may use, so I left it and listed it instead of deleting it.

**Teach-back (`infrastructure/db.py`, `utc_now` and `as_utc`, chosen by the thread):** Every table that records when a row was written uses `utc_now()` as its default, so the whole engine stamps times the same way from one function. SQLite has no time-zone type, so a UTC time comes back without its zone, and Python refuses to compare that with a zoned time. `as_utc()` puts the zone back before any comparison.
