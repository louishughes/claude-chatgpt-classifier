### 2026-10-30 14:10 UTC — ING-015: erasing a chat keeps a note that quotes it, and says so (#405)

**What:** the clean review of the note import found a clash between two features. If you import a note that quotes a chat and then erase that chat, the erase's own check finds the chat's words still in the database, inside the note. So the erase is marked "residual" forever, and there was no way to fix it.

**Louis's decision:** asked on a decision card, Louis chose "keep the note, say so". A note is your own separate file, so erasing a chat shouldn't quietly change it. The erase now:
- still searches for every "can anyone still find this?" passage, and still looks for it in the vault, even when a note holds it. It only leaves those passages out of the raw database-file scan, where the note's own copy is meant to be;
- lists each note that holds one of those passages in the report (`kept_in_notes`): the note's ID, file name, line locator, which version, and whether that version is the current one. It never includes the text. The plain-text message says so too;
- treats a note's text, headings, file name and links as kept source text, the same way it already treats other chats that mention the erased one.

**Split:** removing a note yourself (`ke remove-doc`) is a bigger job with its own plan, token and check, so it became its own ticket, #408, instead of growing this one.

**A clean review of the fix (fix attempt 2).** My first version simply skipped any passage a note held. A reviewer with no history showed the problem: if a note quoted the whole chat, the erase ran with zero passages to check, so a leftover vault file or a stale search index passed as "clean". That is exactly the kind of quiet retention the erase exists to prevent. The fix is narrower now. Only the one scan that a note can legitimately trip skips the passage. The review also caught that a note heading naming the chat still failed the check, that old versions of a note were listed as if current, and that the plain-text message didn't mention the notes.

**Checks:** 5 new tests. One imports a note quoting a chat, erases the chat, and checks that the erase is verified, the note is named, the file is untouched and the note's rows stay. Another checks that an erase with no notes names none. Both fail on main. Three more come from the review: a leftover vault file is still caught when a note quotes the chat, an old version of a note is named as old, and a heading naming the chat isn't counted as a leftover. The existing purge tests pass unchanged.

**Fix attempts:** 2 of 3.

**Teach-back (`retention/purge.py`, the probes):** Before an erase deletes anything, it picks a few short passages of the chat's own words and keeps them only in memory. Afterwards it checks that search and the raw database file can't find any of them. When an imported note, which is kept on purpose, holds one of those passages, the passage is still searched for everywhere except the raw database file, where the note's copy is supposed to be. The report then names the note.

**Talking points:**
- "Two features can each be right and still clash. Here the clash was erase versus import."
- "When the fix is a product rule, the owner picks. I gave Louis two options and a recommendation."
- "The erase report names the notes it kept, but never copies their text into the audit log."
