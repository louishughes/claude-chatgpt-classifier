### 01:10 — REL-006: a person can state or retype a link between two chats (#382)

**What:** The second spec audit found that a "continues" link could never exist. The kind and the `human` evidence class were both defined, but nothing created either one, and `ke related review` could only accept, reject or supersede what a detector proposed. CLAUDE.md §2B asks for continues / forked_from / related_to links that keep their direction and history.

Now:
- `ke related add B continues A --reviewer louis [--note]` stores an accepted link, with evidence class `human` and confidence 1.0. Its history starts with that person's accept.
- `ke related review REL accept --as continues` (or `--reverse`) retypes a candidate. The old row is marked superseded, and a new hand-made link names it in its evidence.
- Notes show the retyped link once, as the person said it. The old one stays in the history.

**Decisions:**
- Only continues, forked_from and related_to can be added by hand. "Quotes" and "references" are facts about the text that a detector can check.
- The old link is never edited in place, because its kind and direction are part of its ID. Retyping always creates a new row and supersedes the old one.
- Adding the same hand-made link twice is refused ("review it instead"), and so is linking a chat to itself.
- `--as` and `--reverse` only go with accept.

**Challenge:** Before this change, superseded links still showed in notes, next to their replacement. The reading code (`relationships/view.py`) now drops a link that a newer one says it replaces. Both rows always touch the same two chats, so the check needs no extra query.

**Teach-back (`relationships/store.py`, `add_human` and `retype`):** `add_human` stores a link a person states, already accepted and marked as known from a human, never from a score. `retype` handles "this candidate is really a continues", or "it points the other way": it supersedes the old row and adds a new human link that names the old one. Every view reads links through one function, so the old one disappears everywhere at once.

**Review:** a clean reviewer with only the acceptance conditions gave a FAIL with one must-fix. If a person retyped a link and then rejected the new one, the detector's original link came back in the notes, because the reading code worked out "what replaces what" only from links that weren't rejected. It now looks at every row. Two should-fix items are also fixed: retyping is now refused unless the link is open or accepted, so a rejection sticks and a link can't be replaced twice; and a needless rollback is gone. "Unknown chat" now exits 1, like "unknown link" in the same command group. A fourth test covers all of this.
