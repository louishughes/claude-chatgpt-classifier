### 01:30 — IMP-009: list, accept or reject a chat whose ID is missing or taken (#380)

**What:** since IMP-002 the importer parks a chat as `review_required` when its export ID is missing, or when another chat in the same export already uses it. Nothing could ever decide one of those, so the chat was never imported and nobody could find it. Now:
- `ke imports candidates` lists every candidate: its ID, the reason, the snapshot and its position in the file, and its content hash. It never shows a title or any words.
- `ke imports candidates review ID accept|reject --reviewer NAME` records who decided and when.
- **accept** gives the chat a logical ID made from its own content hash (`content-sha256:<hash>` stands in for the export ID). The next import of that export brings it in under that ID, and only once. A colliding chat stays a separate chat and is never merged into the one it collided with.
- **reject** keeps it out of every later import. The report counts it as `rejected_candidate`.

**Decisions (delegated by Louis's /goal: "use your own judgement"):**
- The chat comes in on the **next import**, not during the review command. The review only has the archived snapshot, while the import also has the export's images and attachments. Importing from the archive alone would mark the chat's images as missing when they aren't.
- A decision is **final**. An accepted chat may already be imported, so turning it into a reject would leave records behind that the candidate row says shouldn't exist. A second review is refused with `already_decided`. An unknown ID exits with code 2.
- The decision lives on the candidate row (three new columns, migration 0033). A separate append-only history table isn't needed because a decision can't be changed.
- Only a chat whose identity is unsafe right now is looked up, so a decision can't change how ordinary chats import. A purge also removes the accepted candidate row along with the chat it became.

**Teach-back (`importer/identity.py`):** When a chat's export ID is missing or already taken, the importer parks it as a candidate instead of guessing who it is. A person can accept it, which gives it an ID made from a fingerprint of its own content, or reject it, which keeps it out. The importer remembers the decision, so re-importing the same export never asks again or adds the chat twice.

**Clean review:** a reviewer with no context, given only the ticket's test conditions, found no blockers and two real bugs. I reproduced both and fixed both:
- **A reordered export merged two chats.** The decision was only looked up when a chat came *second* with a shared ID. With the export reversed, the accepted chat came first and was folded into the other chat's ID. Now every chat is looked up by its exact content hash, whatever the order, and a collision still waiting for review stays parked even when it comes first.
- **A purge brought the chat back as a new candidate.** The purge deleted the decision along with the chat, so the next import asked about it again. The import now checks the purge tombstone of the content-derived ID first. If a chat collided with a purged one but was accepted as its own chat, it keeps its decision, and only the pointer to the purged chat is cleared.
- Smaller points: a blank `--reviewer` is refused. The docs now say that a chat with no ID whose words change in a later export becomes a new candidate. Two tests cover the bugs above (7 in the file now).

**Talking points:**
- "A chat with no ID isn't lost any more: I can list it, accept it under an ID made from its own content, or reject it."
- "Accepting a chat that shares an ID with another one never merges the two."
