### 2026-10-30 13:25 UTC — Main checked after a merge that skipped CI, then NOTE-038/039 from a clean review (#398, #399)

**What happened first:** five PRs had been merged on Louis's PC and pushed straight to `main` without the usual pull-request checks. So the first job was to check `main`. GitHub had still run the full check on that push: Windows and Linux, Python 3.12 and 3.13, all green, and last night's nightly and clean-install checks passed too. A full local run agreed. Nothing to fix.

**Then two clean reviews.** Two of those merges (#386 open questions across chat parts, #396 note import) had not had a final independent review. Each got a reviewer with no history: only the diff, the ticket and the code. Every finding had to come with a probe run against the real functions, and I re-ran the probes myself before filing anything.

**What the #386 review found (now #398 and #399):**
- *A real open question could vanish.* When two parts listed the same question and the second copy's quote was wrong, the copies were joined, and the later quote check then threw the whole question away.
- *"C++" and "C#" were the same question.* The matching key only kept letters and digits, so "$50" and "50%", "x > y" and "x < y", "1,500" and "1.500" all collapsed too.
- *A "yes" to one offer closed a different question.* "Shall I draft the letter to the council?" and "Yes please" closed the unrelated "Is the deadline Friday?", because the two shared one word.
- Smaller: "Yes, no hotel" counted as a clean yes; a dropped answered question left no flag; six joined copies broke the five-quote limit.

**How it was fixed (`digest/questions.py`, version `note-039-v1`):**
- A copy joins only with the quotes that really are in the cited message. A copy with no good quote stays apart, gets flagged as before, and can't take the real question down with it. At most five quotes are kept, the latest.
- The key keeps symbols that change the meaning (`+ # $ % - < >`, a `.` or `,` inside a number). "10²" no longer reads as "102".
- An offer only counts as "this question" when one offer sentence holds the question's words with at most one missing.
- A reply that says yes and no ("Yes, no hotel", "No thanks, book it") answers nothing.
- An answered question whose quote fails still leaves a flag.

**Checks:** the existing 27 tests for this code pass unchanged, and 30 new ones (one per probe, from both reviews) pass. Full local CI below in the PR.

**Fix attempts:** 1 for the code. One more for the decline rule: the first version said "No thanks to the sales chart" was mixed, which an existing test caught. It now only treats a no as mixed when it also says yes or tells the assistant to do the thing ("book it").

**A clean review of the fix itself (fix attempt 2).** Before merging, a third reviewer with no history checked the fix and compared old and new behaviour on the same inputs. It found two things the fix had made worse:
- A repeat with a bad quote was now left out completely, so the code forgot that the later part had listed the question. A reply that part had already seen could then close it. Now the repeat still counts as "listed here", but its bad quote isn't copied.
- "No need to book it" was read as mixed, because "book it" looked like an order. A verb after "to" or "not" no longer counts as one.

It also found the new rules were stricter than they needed to be. Only a short list of symbols now counts, so an emoji, a dash or `**bold**` no longer stops the same question from joining. Words like "does", "want" and "you" are ignored when matching an offer, so "Would you like a Python version?" still answers "Does the user want a Python version?". One gap is left on purpose: offers that only say "it" ("Want me to book it?") can't be matched to a question by its words, so those questions stay open. That is the safe direction. Version `note-039-v2`, and 9 more tests.

Fix attempts: 2 of 3.

**Teach-back (`digest/questions.py`):** A long chat is summarised in parts, so the same open question can show up twice and an offer can be answered in a later part that the first part never saw. This module joins exact repeats and sets aside offers the user plainly said yes or no to right afterwards. It is deliberately strict, because keeping a question by mistake costs one line, but dropping a real one hides something the user still has to do.
