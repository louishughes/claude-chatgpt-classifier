### 23:05 — UI-009: filter chats and search by category and date in the browser (#363)

**What:** PRD journey 4 is "filter by project, category, date". The browser's chat list could only search titles, and the search page had no filters. Now /chats has a Category list (each approved term or project that labels at least one chat, with how many) and "started on or after / before" dates. /search has dates, "said by" and the same Category list, all checked by the RET-009 code that `ke search` and the API use. Paging keeps every filter.

**Decisions:**
- The Category list only offers labels that are actually on a chat. An approved term no chat carries would be a dead end.
- A bad date or an unknown category on /chats says so in a sentence and shows the unfiltered list, rather than an empty page that looks like "no chats". On /search a refused filter means nothing is searched, with the reason shown, because search results under a filter you didn't get would mislead.
- Following the RET-009 review's nit, a refused term no longer names the vocabulary version it was checked in, so no part of the request comes back in the error.

**Challenge:** The test kept a database row object after its session closed, and SQLAlchemy refused to read it. The fix was to copy the ID out before closing.

**Independent review:** a separate session with only the acceptance conditions passed it with two should-fix findings, both fixed before the PR: an approved category on no chat yet was called "not in the vocabulary" (now it's an honest "0 chats"), and every search page view read every chat's labels just to fill its Category list (it now reads only the published vocabulary; only the chats page, which shows counts, does the full pass). Its two nits were fixed too: a refused filter no longer makes the summary say "filtered", and paging links lost a stray "&". Two refused filters now both get their own sentence.

**Teach-back (`chat_categories` in `ui/data.py`):** It takes the newest published vocabulary and, in one pass over every segment, collects which chats each label is on, using the labels in force. It keeps only labels approved in that version and sorts them by kind and name. The chat list then shows only chats whose IDs are in the chosen label's set.
