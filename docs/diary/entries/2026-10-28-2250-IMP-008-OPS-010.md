### 22:50 — IMP-008 and OPS-010: how long an import took, and roughly how many tokens each model stage used

**What:** Two gaps the spec audit found. The PRD's import dashboard asks for stage timings, so every import report now records seconds for archive, parse, identity and revisions, media, links and mentions, relationships, and the total. `ke imports report` and the import page show them under "How long it took". The PRD also asks for per-stage token estimates, so `ke eval tokens` reads the model ledger and prints, for digest, extract and classify, how many requests were sent, how many have a stored answer, and estimated input and output tokens. It shows counts only, never text, and it makes no calls.

**Why this way:** Timings change every run, and the report's `to_dict` is what idempotency and backend checks compare. So the timings sit beside it (`to_stored`), not inside it. Parts round down and the total rounds up, to the millisecond, so the parts never add up to more than the total. Token counts use one rule, characters divided by four and rounded up, which is the same rule the run budget's size check already used. It is labelled an estimate, not a bill. "Cached" means the answer is stored, so a re-run gets it with no model call. The ledger doesn't count individual cache hits, and adding that would need a schema change this ticket doesn't call for.

**Teach-back (`_Stopwatch` in `importer/run.py`):** It keeps a running total of seconds for each stage of one import. Each stage is wrapped in a `with clock.stage(...)` block, and parsing is timed by measuring how long each "give me the next chat" takes, because the adapter parses lazily. At the end, the totals are rounded and stored with the report, where the CLI and the page read them back.
